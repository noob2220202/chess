# 증강체스 분석 & 밸런스 로드맵 (1단계: 현황 파악)

기준: augmentchess.org, 카탈로그 v19 (2026-09-27 업데이트 반영). 전체 카드는 `docs/cards.md`, 원본 데이터는 `data/cards.json`.

## 1. 게임 구조 요약

- **모드**: 일반(0·10·20수에 3장 중 1장, 총 3장) / 카오스(2장 묶음 3개 중 선택, 총 6장) / 그랜드(공용 28장 풀에서 번갈아 6장씩, 선택 20초) / 캠페인(시나리오)
- **카드 종류**: 능동(턴 소모 없음, 180장) / 패시브(62장). 카테고리: OPENING 34 · MIDDLE 87 · END 61 · PIECE 37 · RULE 23 = **242장**
- **승리**: 킹 포획. 45수 이후 10수간 비가역 변화가 없거나 3수 동형이면 *카드 총합이 낮은 쪽* 승리. 무브 불가 시 패배
- **시계**: 수당 +15초
- 멀티플레이는 베타(방 코드 기반 1:1), 계정 시스템·채팅 있음. **레이팅/랭크는 현재 없음**

## 2. 가장 중요한 발견: 밸런스가 "수동 별점"에만 의존

- 각 카드에는 `ratingHalfStars`(0.5 단위 별점)가 있고, **드래프트 가중치는 별점의 단순 함수**다.

| ★ | 0(RULE) | 1.5~2.5 | 3.0 | 3.5 | 4.0 | 4.5 | 5.0 |
|---|---|---|---|---|---|---|---|
| 가중치 | 9 | 9 | 8 | 7 | 6 | 5 | 4 |
| 카드 수 | 23 | 52 | 53 | 59 | 35 | 11 | 9 |

- 즉 **실제 승률 데이터 없이 운영자의 감**으로 강한 카드를 덜 뽑히게 하는 구조. 카드가 242장으로 늘어나는 속도(최근 3주간 약 47장 추가)를 감안하면 상호작용 조합(약 29,000쌍) 검증은 수동으로 불가능.
- 카드 총합(★)이 낮은 쪽이 시간제 결승 판정에서 이기는 규칙이 있어, **★ 오류는 드래프트 확률뿐 아니라 승패 판정에도 직접 영향**.
- 같은 카드의 ★/문구가 업데이트마다 바뀜(예: 회전문 ★3.5↔3.0, 그릭 기프트 ★3.5↔3.0이 번들 내 버전 간 차이) — 튜닝이 잦고 근거가 기록되지 않음.

## 3. 눈에 띄는 불균형 후보 (가설 — 승률 데이터로 검증 필요)

| 유형 | 예시 | 우려 |
|---|---|---|
| 즉승/게임 종료형 5★ 계열 | 하이랜더(중복 기물 없으면 즉시 승리), 종전(3수간 무포획 시 즉승), 트롤리 | 상대가 막을 수단이 없거나 선택 압박만 큰 "원 샷" 카드. 카운터플레이 유무가 핵심 |
| 판 리셋형 | 청바지(양측 메이저 피스 추방), 몽골리안 갬빗, 호드, 붕괴, 소멸 | 분산이 크고 선/후공·드래프트 순서에 따라 결과가 갈림. 기술 차이가 안 드러남 |
| 카드 복제/재사용 | 복제, 조커 | 상대 카드 의존도가 커서 ★ 고정이 부적절. 상황별 가치 편차 큼 |
| 저평가 후보 | 견습 기사단·풍차·강제 교환(1.5★) | 실제로 약한지, 단지 설명이 약해 보이는지는 데이터 필요 |
| 무작위 요소 | 이세계, 독이 든 폰, 소멸, 체스 344200 등 | 스포츠화에는 분산 억제 필요 |
| 선후공 | 흑 처리 문구가 있는 카드(d4→d5, 겨울 왕국 등) | 선공 이점 + 오프닝 카드 상호작용 |

## 4. 스포츠화 / 레이팅 설계 방향 (제안)

1. **카드 평가를 데이터화**: 모든 대국에서 (양측 카드, 선후공, 결과, 수 수)를 기록 → 카드별 *한계 승률*(해당 카드를 가졌을 때 승률 − 기대치)과 쌍 승률 산출. ★은 이 값으로 자동 보정.
2. **레이팅**: 드래프트 운이 섞이므로 Elo/Glicko-2에 *카드 강도 보정 항*(기대 승률을 카드 합 차이로 조정)을 넣는 방식 권장. 시즌제 + 배치 10판.
3. **공정한 드래프트**: 같은 카드 풀을 흑/백이 *미러*로 받는 모드(양측이 동일 3장 선택지를 번갈아 선택)나 그랜드 모드를 랭크 기본으로. 순수 랜덤 3장 드래프트는 캐주얼 전용.
4. **분산 큰 카드 분리**: 즉승형·판 리셋형·RULE 카드는 *랭크 풀에서 제외*하거나 별도 "카오스 큐"로 분리. 랭크용 코어 풀(약 100~120장)을 정하는 것이 가장 효과 큼.
5. **밴/픽**: 이미 밴 시스템 존재. 랭크에서 선수당 1~2장 밴 + 밴 통계 공개.
6. **결승 판정 개선**: "카드 총합 낮은 쪽 승리"는 ★ 정확도에 종속 → 데이터 기반 가치나 단순 규칙(예: 기물 가치 합)으로 교체 검토.

## 5. 앱 개발 관점 (다음 단계에서 결정)

- 규칙 엔진이 핵심 리스크: 카드 242장 × 상호작용. **엔진은 순수 함수형(상태, 행동 → 새 상태), 렌더링과 분리**해서 서버 검증·AI·시뮬레이션(셀프플레이로 밸런스 수치 산출)에 재사용.
- 후보 스택: TypeScript 코어 엔진(공용) + React Native/Expo 앱 + 서버(Node, 권위 서버로 부정 방지) + Postgres(대국 로그·레이팅).
- 카드는 `data/cards.json` 형태의 **데이터 + 효과 모듈**로 분리해 패치 배포를 쉽게.

## 6. 제안 진행 순서

1. (완료) 카드 242장 수집, 구조 분석
2. 카드 효과 설명을 기능 단위로 분류(이동 규칙 변경 / 소환 / 제거 / 즉승 / 랜덤 등) + 고분산·무카운터 후보 리스트 확정
3. 코어 규칙 엔진 MVP (일반 체스 + 카드 10~20장) + 셀프플레이 시뮬레이터
4. 시뮬레이션으로 카드별 승률 측정 → ★/가중치 재산정
5. 레이팅·매치메이킹·앱 UI

## 참고/주의

- 데이터는 사이트 클라이언트가 제공하는 공개 카드 설명에서 가져왔으며, 효과의 *정확한 구현 규칙*(예: 상호작용 우선순위)은 설명만으로 알 수 없는 부분이 있음. 상업적 앱으로 만들 경우 원 제작자의 카드 이름·일러스트·문구를 그대로 쓰지 말고 **자체 카드/규칙으로 재설계**하거나 허락을 받는 것이 안전함.
